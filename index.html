🔐 Password Audit via GitHub Issues

Powered by John the Ripper — open an issue, get an instant security report on your password's strength.

✅ Fully Automated 🤖 GitHub Actions ⚠️ Educational Only

🧭 Overview

This repository is equipped with a GitHub Actions workflow that lets any user audit a password's security by simply opening a GitHub issue. The workflow automatically:

  • Detects issues with the title crack
  • Extracts the password (and optional flags) from the issue body
  • Hashes the password and runs John the Ripper against it
  • Analyses entropy, character classes, and overall strength
  • Posts a formatted audit report pinging you in a comment
  • Redacts the password from the issue body and closes the issue
ℹ️
What is John the Ripper?
John the Ripper is a well-known, open-source password security auditing and password recovery tool. It supports hundreds of hash types and is used by security professionals worldwide to test password strength.

🚀 Quick Start

  1. Open a new Issue
    Navigate to the Issues tab and click New issue.
  2. Set the title to crack (exactly, case-sensitive).
    The workflow only fires when the title matches this word.
  3. Enter the password in the body
    The first non-empty line of the body is treated as the password. You can optionally add flags on subsequent lines (see Flags). 
    MyPassword123!
  4. Submit the issue.
    The workflow starts immediately. Within 1–3 minutes you will receive a comment on the issue with your full audit report, then the issue is closed.

Example with flags

H3ll0W0rld!
--hash=sha256crypt
--time=60
--mode=auto

This audits the password H3ll0W0rld! using a SHA-256 crypt hash, a 60-second time budget, and automatic attack mode selection.

📝 Issue Body Format

The issue body supports a simple, human-readable format: 

<password>
[--flag=value]
[--flag=value]
...
LineDescriptionExample
Line 1 The password to audit (required). Maximum 256 characters. MyP@ssw0rd!
Line 2+ Optional flags, one per line, in --key=value format. --time=60
⚠️
Lines that start with -- are treated as flags, not as part of the password. The first non-flag, non-blank line is always the password.

⚙️ Available Flags

All flags are optional. If omitted, sensible defaults are used.

Flag Values Default Description
--hash sha512crypt, sha256crypt, md5crypt sha512crypt Hash algorithm used to create the test hash that John will attempt to crack. Stronger hashes (SHA-512) are slower to crack, giving a more realistic simulation of a modern Linux system.
--time Integer: 10 – 120 30 Maximum number of seconds John is allowed to run. A higher value allows more thorough attacks but takes longer. Values outside the 10–120 range are clamped automatically.
--mode auto, wordlist, incremental, single auto Attack mode used by John the Ripper (see mode descriptions below). auto tries wordlist first, then incremental with the remaining time.

Attack Modes (--mode)

🔤 wordlist — John tries every entry in its built-in wordlist (password.lst) plus common mangling rules (e.g. capitalise, append digits). Fast, and highly effective against common or dictionary-based passwords.

🔢 incremental — John generates candidates character-by-character using statistical frequency data. Effective against short and medium-length passwords of any complexity.

👤 single — John uses contextual information (username, GECOS fields) combined with mutation rules. Effective against passwords that are simple transformations of the username.

🤖 auto (default) — Splits the time budget in half: first runs wordlist mode, then incremental mode if the password has not yet been cracked.

Hash Algorithms (--hash)

ValueAliasFormat prefixNotes
sha512crypt sha512 $6$ Modern Linux default. Very slow to crack — recommended.
sha256crypt sha256 $5$ Also used on Linux. Somewhat faster than SHA-512.
md5crypt md5 $1$ Legacy; much faster to crack. Use for quick tests only.

What "Cracked" Means

If John the Ripper finds the password within the time limit, it reports "Cracked". This means the password is weak enough to be discovered using automated tools in a short time — a real attacker would likely succeed.

"Not cracked within time limit" does not guarantee the password is safe. It only means John could not find it within the allocated time on GitHub's shared runners. A dedicated attacker with specialised hardware could still crack it.

What "Entropy" Means

Entropy measures the unpredictability of a password. Each bit of entropy doubles the number of guesses an attacker needs. 60 bits ≈ 260 ≈ 1.15 quintillion guesses. Modern GPUs can test billions of md5crypt hashes per second, so only high-entropy passwords with slow hash functions are truly safe.

🛡️ Security & Privacy

🚨
Never submit a real, currently-used password.
GitHub issues are public. Anyone can see the issue body before it is redacted. Always use a fictional or already-retired password for testing purposes.
⚠️
What happens to your password?
The workflow masks the password in workflow logs using GitHub's ::add-mask:: mechanism. After the audit is complete, the issue body is automatically replaced with [Password redacted after audit completed] and the issue is closed. However, the password is visible in the issue body for the duration of the workflow run (typically 1–3 minutes).

Tips for Safer Password Auditing

  • Audit passwords you are considering using — not ones already deployed.
  • Change any real password before submitting it here.
  • Prefer passphrases (four or more random words) over complex short passwords.
  • Use a dedicated password manager to generate and store high-entropy passwords.
  • Enable multi-factor authentication wherever possible — even a cracked password cannot be used without the second factor.

⚙️ How it Works — Technical Details

  1. Issue opened — GitHub fires the issues.opened event to the workflow.
  2. Title check — The workflow only runs if github.event.issue.title == 'crack'.
  3. Body parsing — The first non-blank, non-flag line is extracted as the password (max 256 characters). Optional --flag=value lines are parsed for hash, time, and mode settings. The password is immediately masked in all subsequent log output.
  4. Complexity analysis — A Python script calculates entropy, character-class usage, and assigns a strength grade based on the NIST SP 800-63B guidelines.
  5. Hash creation — openssl passwd creates a salted crypt hash of the password (SHA-512, SHA-256, or MD5 crypt), stored in a temporary file. The password is passed to OpenSSL via an environment variable to prevent shell-injection risks.
  6. John the Ripper — The john binary (installed from the Ubuntu package repository) attempts to crack the hash within the time limit using the selected attack mode.
  7. Report generation — Results (statistics, strength verdict, crack outcome, entropy meter) are formatted as a Markdown comment using the GitHub Actions Script action.
  8. Cleanup — The comment is posted mentioning the issue author, the issue body is replaced with a redaction notice, and the issue is closed.

❓ Frequently Asked Questions

Why does my issue say "0 password hashes cracked, 1 left"?

This means John the Ripper did not crack your password within the allocated time using the chosen attack mode. Try increasing --time or switching to --mode=incremental for a more exhaustive search. Keep in mind that a strong password may never be cracked by incremental attack in any reasonable time frame — which is a good sign!

Can I submit multiple passwords in one issue?

No. Only the first non-blank, non-flag line is treated as the password. To audit multiple passwords, open a separate issue for each one.

Why is the "Hardware speed" value important?

The benchmark speed tells you how many candidate passwords per second the GitHub runner can test against your chosen hash format. SHA-512 crypt is intentionally slow (designed to be slow to resist brute-force). A real attacker with dedicated GPU hardware can test millions or billions of candidates per second, so even "not cracked here" can mean "crackable with more resources".

What wordlist does John use?

The workflow uses John the Ripper's built-in password.lst (approximately 3,000 of the most common passwords). This is intentionally limited to keep audit times predictable. A real-world attacker would use wordlists with hundreds of millions of entries (e.g. RockYou, HaveIBeenPwned corpus). If your password is not cracked by this wordlist, it does not mean it would survive a full attack.

Why is the issue body replaced with "[Password redacted…]"?

To reduce the window of exposure. Even though the issue is public while the workflow runs, replacing the body after completion limits how long the password text appears in GitHub's UI and search indexes.

Can I run the audit on a private repository?

Yes. If you fork this repository and make it private, the issues will be private too. The workflow uses only built-in GitHub tokens and does not send data to any external service.

The workflow didn't run — what happened?

Check that the issue title is exactly crack (lowercase, no extra spaces). Also verify that GitHub Actions are enabled for the repository under Settings → Actions → General.
